# Capability Register

What the tooling has *proven* it can and cannot do, each entry dated with the evidence. This file exists so a limit discovered in one engagement is never re-discovered (or wrongly assumed away) in the next, and so capability claims in deliverables rest on tests, not memory.

Rules: entries come from actual tests or official docs, never from assumption. Claude appends new entries dated and marked `[unreviewed]`; the user confirms them at the next retro (drop the marker) or corrects them. When a capability changes (tool update, new release), update the entry, don't duplicate it. If a session is about to assume something this file contradicts, the file wins until re-tested.

## NetSuite MCP (assessment/discovery connectors)

- **The MCP connection consumes a full user license; an Employee Center role/license cannot carry it.** The connector role needs Setup-category permissions (MCP Server Connection, Log in using OAuth 2.0 Access Tokens, plus REST Web Services for the standard tools), which Employee Center roles cannot receive (EC permission lists are fixed; only levels change), and EC-license users can only hold EC-type roles. Administrator and full-permission roles are excluded by Oracle at the other end, so the connector needs a middle-band custom role on a full seat, a dedicated integration user (optionally Web Services Only) or an existing full user. Seat availability is an onboarding conversation on license-constrained clients. Docs-chain verified 2026-07-30; sandbox-confirmed at the 2026-08-16 triage: the MCP Server Connection permission is not offered on EC-type roles.
- **The NetSuite MCP connection is always a manual, up-front onboarding step.** It requires NetSuite's own **MCP Standard Tools SuiteApp** (free) installed in the client account, plus Server SuiteScript, REST Web Services, and OAuth 2.0 enabled, a **dedicated connector role (Administrator is not allowed)**, and the auto-created integration record enabled on first connect. SuiteApp installs have no programmatic path, so a client admin does this before any MCP-dependent work; build it into engagement kickoff and get client permission explicitly. Oracle-docs-verified 2026-07-30.
- **"Record 'X' was not found" on a valid SuiteQL table means the connector role lacks permission for that record type.** Not a query-syntax problem. Diagnose by running the same query shape against a known-good table (e.g., `location`, `employee`). The mechanism is the dedicated non-Administrator connector role's permission set. **Fix: connect through the standard Power Cloud role** (`customrole_pc_mcp_ai_connection`, shipped in the ScriptReader project) instead of an ad-hoc role; its master grants 224 permissions including `LIST_ACCOUNT`, `LIST_CLASS`, `LIST_COMPANY`, and `LIST_COMPANY_FEATURE_SETUP`, the tables ad-hoc roles miss. Verified 2026-07-29 (Shinesty: `account`/`accountingperiod`/`classification` blocked under an ad-hoc "Claude Admin" role); role-file evidence confirmed 2026-07-30; live connections have since run through the standard role and standard tables read correctly (confirmed at the 2026-08-16 triage).
- **Account ID, NetSuite release, and the enabled-features list are not SuiteQL-queryable at all.** Read from the UI (Setup > Company > Company Information / Enable Features) or via an `N/config` script. Chasing them with queries always fails. Verified 2026-07-29.
- **`ns_getSubsidiaries` returning `[]` means a single-company (non-OneWorld) account.** Correct behavior, not an error. Verified 2026-07-10 (Shinesty).
- **Account identity can be confirmed via employee email domain** when identity tables are blocked (`SELECT COUNT(*) FROM employee WHERE email LIKE '%@client.com%'`). Verified 2026-07-29.
- **Multiple NetSuite connectors may be wired in one environment** (a client account and Power Cloud's own). Always confirm which account a connector points at before querying; on 2026-07-29 one connector was Power Cloud's own account, not the client's.
- **Script Reader toolset** (`listScripts`, `readScriptSource`, `getScriptDeployments`, `readFile`) enables reading actual script bodies and deployment status; without it, claims about what a script *does* cannot be [Verified]. Requires SuiteScript read permission on the connected role (fixed mid-session 2026-07-10 on Shinesty).
- **The ScriptReader SDF project is the standard per-engagement install** (`C:\Development\Projects\Netsuite Development\MCP\ScriptReader`, an ACP, deploys to any administered account, no SDN id needed). One deploy ships both the four read-only tools and the standard MCP connection role `customrole_pc_mcp_ai_connection` (master source of truth at `roles/customrole_pc_mcp_ai_connection.master.xml`, full-OneWorld variant, with `scripts/set-role-variant.js` generating the deployable variant per account type). Standard onboarding: client admin installs NetSuite's MCP SuiteApp; we deploy ScriptReader with the client's go-ahead; the MCP connection uses the shipped role. Permission gaps found on any engagement get fixed in the role master so every future engagement inherits them. Recorded 2026-07-30.

## NetSuite Saved Search construction

- **NetSuite's Saved Search UI does not offer transaction subtypes (e.g. "Customer Payment") as their own base search type.** Only the generic "Transaction" search type exists in the type picker; subtypes are selected via a `Type` filter value within it (a direct URL for `searchtype=CustomerPayment` 404s). A fix that assumes a subtype-specific base record must instead be achieved through return-field / join choice on a generic Transaction search. Verified live 2026-08-17 (Brixton).
- **"Applying Link Amount"/"Applying Transaction" and "Applied To Link Amount"/"Applied To Transaction" are direction-specific, and easy to swap by mistake.** On a search of the transaction that *initiates* an application (e.g. a Customer Payment applying to invoices), the correct join is "Applied To ___" (this transaction is applied TO the other side), not "Applying ___" (for the transaction *receiving* an application, e.g. what a deposit applies to this record). Verified live 2026-08-17 (Brixton): `PYMT0003173` applying to `INV0086195`, `Applied To Link Amount` = 357.12 (matches the payment's own Apply tab and the REST record API's `apply.items[].amount`); `Applying Link Amount` returned blank for the same row.
- **On a Transaction search filtered to `Type = Payment` with `Mainline = False`, the "Applied To Link" join fans out one extra row per invoice for early-payment discounts**, on top of the real payment-applied row — even though the payment's own GL Impact aggregates all discounts into a single Discounts-account debit line, with no per-invoice discount GL line at all. The discount pseudo-row carries the same "Applied To Transaction" (invoice) and a real, non-zero "Applied To Link Amount" (matching that invoice's own Disc. Taken figure), so a naive per-invoice read silently includes phantom discount rows alongside the real payment rows.
- **The clean discriminator is a boolean field literally named "Paid Amount Is Discount"** (surfaces by searching the field picker for "discount"), not the link-type field: "Applied To Link Type" returns "Payment" identically for both the real payment row and the discount row, so it cannot distinguish them. Filter `Paid Amount Is Discount = No` to keep only the real applied-payment rows. Verified live 2026-08-17 (Brixton): `PYMT0002887` (6 real invoice applications + 2 discount-fan rows) — the two discount rows (33.05, 55.20, summing exactly to the payment's $88.25 aggregate Discounts GL line) were the only ones with `Paid Amount Is Discount = Yes`. `[unreviewed]`

## SuiteQL / SuiteScript record quirks

- **`[unreviewed]` `transactionline.quantity` is stored negative for lines on a sales-direction transaction** (Sales Order confirmed; likely any transaction that decreases inventory - Invoice, Cash Sale, Item Fulfillment - unconfirmed on those). `quantityshiprecv` on the same line is not affected the same way and reads positive. The record-API/UI layer (`N/record`, the REST record endpoint) abstracts this and shows a positive quantity; raw SuiteQL against `transactionline` does not. Confirmed on Bixbi (2026-09-03): a report built from raw SuiteQL showed negative "Qty Adjusted" until every read of `quantity` was wrapped in `ABS()`. Worth checking for on any future SuiteQL-based report or script touching `transactionline.quantity` directly, especially one whose values will be compared against or combined with a UI/record-API-sourced quantity (which won't have the same sign).

- 2026-10-05 [unreviewed] **A SuiteQL error that does not name the column usually means the column or function does not exist, and the real names are not the obvious ones.** (GW) "An unexpected SuiteScript error has occurred" and "Search error occurred: Invalid or unsupported search" came back for non-existent identifiers (`BUILTIN.FISCAL_MONTH_PERIOD`, `transactionline.itemid`, `transaction.salesrep`, `transactionline.pricelevel`), so reproduce by running the single suspect expression alone. A `FETCH FIRST n ROWS ONLY` query can also report a misleading "syntax error near FETCH" when an earlier column is wrong; the same query with `ROWNUM <= n` surfaced the real "Unknown identifier" message. Verified real names: the sales rep on a transaction is `transaction.employee`; the price level on a line is `transactionline.price` (an id into the `pricelevel` table, whose rows are named like "SR"); kit child lines are flagged `transactionline.kitcomponent = 'T'` and repeat the Kit's quantity with a null `netamount`, so summing quantity double counts; the item's text code is `item.itemid`; a period label is `BUILTIN.DF(t.postingperiod)` ("Jan 2026"), and ordering by that label is not chronological, use `MIN(t.postingperiod)`. `BUILTIN.DF(c.<segment>)` on a customer returns its CURRENT value, so a report keyed on it restates history when customers are reclassified.

- 2026-10-09 [unreviewed] **A multi-select field in SuiteQL can't be used as an ID: `TO_CHAR` on it returns the literal text "RELATIONSHIP FIELD", so string matches and joins on it silently return zero rows instead of an error.** (Teppermans P10, production) A plain `SELECT` of the field displays an ID, which makes the problem easy to miss. Concatenating it into an `INSTR` match against a JSON field matched nothing across about 20,000 rows, while the same match by literal ID matched. Fix: join through the field's map table, `map_{recordtype}_{fieldid}` (`mapone` = the record's id, `maptwo` = the selected id), e.g. `map_customrecord_mhi_dt_shipping_record_custrecord_mhi_dt_sales_orders`. Before trusting an all-zero count, check the query against one row whose answer is already known.

## SuiteFlow (Workflow)

- **SuiteFlow cannot do line-level conditional logic on a transaction's sublist.** A workflow's Set Field Value action targets a single field on the triggering record; there is no construct to loop over a sublist or branch per-line (e.g., "only the Credit line," "only lines where account = X"). Journal Entries compound this further by having no "main line" concept the way other transaction types do (a Vendor Bill's expense line, a Sales Order's item line), which is what workflow line-targeting on other record types relies on. Any requirement of the shape "update field X on lines matching condition Y" on a JE (or likely any transaction, for the sublist-loop limitation specifically) requires a `beforeSubmit` User Event script with a `getLineCount`/`getSublistValue` loop instead. Confirmed 2026-09-23/28 (Upward, Navan Integration custom project).

- **`[unreviewed]` `N/ui/serverWidget` Form's `addSubmitButton()` submits via POST, not GET.** A Suitelet `onRequest` gated with `if (context.request.method !== 'GET') { return; }` (a natural-looking guard, and what a "GET-only, no side effects" page seems to call for) silently produces a blank page with zero output on every submit, since the early return exits before anything is written to the response — no exception, no log entry, nothing to catch even with a try/catch wrapped around the rest of the handler. `context.request.parameters` reads identically regardless of method, so the fix is simply not gating on method at all when the Suitelet has no reason to distinguish GET from POST. Cost real back-and-forth on Bixbi (2026-09-03): first assumed the blank page was an unhandled exception, added error-handling and better date parsing, redeployed, same blank result — the actual cause was the method check, unrelated to either fix attempted first. Diagnostic tell: a Suitelet page that goes fully blank (not even a NetSuite system error banner) on form submit, when the handler has a `request.method` check, should make that check the first suspect, before assuming a script logic bug.
- **Confirmed:** a script deployment's `Status` field (Testing/Released/Not Yet) and its `Deployed` checkbox are two independent switches — Status showing Released does not mean the script is live. `Deployed` (`isdeployed` in SDF) is the actual on/off toggle; a deployment can sit at `Status: Released`, `Deployed: unchecked` indefinitely as a deliberate "ready to activate" state, and it will not fire. On Upward (Navan Integration, 2026-09-25 through 09-28), a deployment was intentionally pushed to prod inactive (`isdeployed=F`) for the customer to review before go-live; the consultant later reported the deployment "released in prod" and the script "doesn't seem to be firing," which read as a possible logic bug. Diagnosis wasted a full round of hypothesis-testing (custom-list value mismatch, deployment audience) before confirming the actual cause: `Deployed` had simply never been checked. A pre-existing SuiteFlow workflow covering one of the same fields (header Memo) masked the symptom further, making the record look partially correct even though the new script had never executed at all — zero Execution Log entries, at any log level, is the tell that a deployment isn't firing at all, versus firing and silently succeeding (the latter requires success-path logging to distinguish, which this script did not have until this incident). **Diagnostic order: always confirm the `Deployed` checkbox specifically, not just `Status`, before investigating trigger-field or audience logic.** Confirmed 2026-09-28.
- **An SDF `scriptdeployment` with no explicit audience tags (`allroles`, `allemployees`, `audslctrole`, etc.) deploys and shows RELEASED, but fires for nobody, not everybody.** Easy to miss: `project:deploy` and `project:validate` both succeed silently with no warning that the audience is effectively empty. On Bixbi (2026-09-03), a User Event script deployed clean, a real line removal was confirmed to have happened on a test Sales Order, and no error appeared anywhere — the script had simply never executed. Confirmed by checking the deployment's Audience subtab in the UI (empty) and fixed by setting it there, then pulling the correction back into the SDF source with `object:import` (adds `<allroles>T</allroles>`). **Always set an explicit audience tag in the scriptdeployment XML** (`<allroles>T</allroles>` for "all internal roles," NetSuite's own validation warning on that tag confirms it doesn't include external/partner roles, which need `<audslctrole>` separately) rather than leaving it to default. Worth a deploy-checklist line and worth sandbox-testing an actual trigger, not just checking `isdeployed`/`status`, before considering any User Event/Client Script task done.
- **SDF `selectrecordtype` (the numeric key a List/Record custom field uses to point at a standard record type) has no published name-to-number mapping anywhere, including Oracle's own SDF XML reference**, which documents the valid value range and feature dependencies but never names. `project:validate` only confirms a guess is *syntactically valid* (a real value exists), not *semantically correct* (three different valid numbers mean three different record types). The only reliable ways to confirm meaning: (a) find an existing unlocked custom field in the target account already using the value needed, via `object:import --type <fieldtype> --scriptid ALL` then grep for `selectrecordtype` across whatever imports (locked/bundle-owned fields can't be imported this way and will fail with "You cannot download the XML file for this object because it is locked"), or (b) deploy with a best guess and have someone with UI access check what "List/Record Type" the field actually shows, correct it in the UI if wrong, then `object:import` the fix back into the SDF source. ## Rendering toolchain

- **python-docx cannot natively produce a clickable TOC or internal cross-reference links.** They require bookmarks plus hyperlink/TOC fields built via direct XML, and the TOC field updates on open via Office COM. Confirm links resolve in the exported PDF. Noted 2026-07-29.

- **Root cause of the Montserrat substitution, and how to detect it.** `Montserrat-VariableFont_wght.ttf` declares legacy family `Montserrat Thin` while claiming `Montserrat` as its *typographic* family, so it shadows the static faces and Word binds to an instance it cannot embed. Every naming then fails: `Montserrat`+bold, `Montserrat` plain, `Montserrat SemiBold`, `Montserrat Medium` and `Montserrat Bold` all exported as Calibri (each probed individually 2026-08-17). Barlow is unaffected because no variable Barlow is installed, and that asymmetry is the tell that separates this from a plain per-user-visibility problem. Not a permissions issue: every file is `fsType=0` (Installable) with correct name tables. **Diagnostic:** open the PDF with PyMuPDF and read `page.get_fonts()`, or extract spans and check `span['font']`; `Calibri-Bold` where headings should be is the signature. **Remedy, and it does NOT need admin:** uninstall `Montserrat-VariableFont_wght.ttf` alone. It registers under the misleading name **"Montserrat Thin (TrueType)"** (Settings > Fonts, search Montserrat, uninstall the face called Montserrat Thin). The four statics then own the family and every naming resolves. Verified end to end on MH Crane 2026-08-17: before removal all five namings exported as Calibri; after removal `Montserrat`+bold gave `Montserrat-Bold`, plain gave `Montserrat-Regular`, and both client PDFs came back with zero Calibri. Removing the variable font also drops the Thin/Light/ExtraLight/ExtraBold/Black weights, which only that file provided and which the brand does not use. Side effect: the document PDF shrank from 608 KB to 221 KB, since the substitution had been embedding far more. `[unreviewed]`

- **Word renders the paragraph mark, and PDF export emits it as a space span in whatever font the mark carries.** Styling only the runs leaves 45 stray Calibri spaces in an 18-page document (one per heading), which puts a Calibri resource in the PDF and makes a "no substitution" check ambiguous.
