The one idea

The folder is the memory. Everything about a client lives in that client's folder: the raw source material, the working evidence, the finished deliverables, the build work. Nothing important lives in a chat history, in a consultant's head, or in a model's context.

The consequence is the whole point. Any consultant who opens a client folder and starts a session is talking to something that already understands the engagement. The context does not have to be rebuilt, re-explained, or remembered. A session can be cleared, a machine can be swapped, a week can pass, and the state survives, because the state is on disk.

Everything below is machinery in service of that one idea.

At the workbench

The engagement types below describe how work gets shaped. Most of the actual week is spent somewhere else: at the bench, with one specific piece of work in hand.

The habit is the same every time. Anything to be strategized, planned, or executed starts by opening Claude inside that customer's folder. Brainstorm there, plan there, and wherever the work allows, build and deliver from there too. There is no thinking tool and separate doing tool, and no point where work leaves the client's folder to happen somewhere else. That is what makes the folder worth treating as the memory.

Brainstorm

Bring the problem and the constraint, not a preferred answer. Naming a solution up front is how you lose the second option.

Plan

Nothing gets built without a written plan: approach, assumptions, and what will be tested to prove them. House policy, not preference.

Execute

Sandbox first, version-controlled, with a human at the plan and again at production.

Deliver

The artifact renders from the same folder, branded, and every client-facing sentence gets human eyes before it leaves.

The stance: managing, not typing

Hand over a substantial chunk and step away, with the license to use judgment and log the decision rather than wait, stopping only for anything that touches a client system. Then check in the way you would on a colleague you delegated to: read what it did, correct course, hand over the next chunk. Watching it work is not billable, so the parallel work gets lined up first. Cost discipline is part of the same habit: the default model for routine work, escalation to the frontier model only for genuinely hard reasoning, and straight back down afterward.

Asking in a way that gets honest answers

These are written down because they were expensive to learn, and because the difference between a good answer and a confident wrong one is usually in how the question was put.

  • Context without leading. Give everything you know, but not your preferred answer. Once your idea is in the prompt, the objectivity is gone.
  • Current state before design. Make it explain how the thing works today before it proposes anything. Skipping this produces confident redesigns of a system it never understood.
  • "What's your source?" For any claim that smells off, ask exactly that. A claim that traces back to a stretch dies before it reaches a client. Never open with "are you sure?", which just invites apologetic reversal.
  • Do not hand it the escape hatch. Say "we can always check with the customer" and it will take that exit instead of reasoning. Make it commit to a recommendation; you decide afterward whether the client needs to weigh in.
  • Steelman the alternative. After it proposes one approach, ask for the strongest case for a completely different one. One prompt, and there is a real comparison instead of a single track.

The three engagement types

Everything we take on is one of three kinds of work. The type is declared in the client's CONTEXT.md at setup, and it decides which workflow runs, which skill owns it, and what the client receives. It is asked at intake rather than inferred, because getting it wrong sends the whole engagement down the wrong track.

Type one

Rapid Assessment / Recovery

An existing NetSuite customer having a difficult time.

We come in, find what is actually wrong, and produce the prioritized menu of work that gets them running again. Discovery-led, six stages.

ShipsAssessment, Presentation deck, Execution Plan

Type two

Implementation

A blank NetSuite account, configured from scratch.

Same discovery machinery, but the output points at a target state rather than a remediation list. Build runs as base setup first, then design sessions per process area.

ShipsImplementation Roadmap, Presentation deck, Execution Plan

Type three

Custom Project

Hired for one specific thing, usually custom development.

Scope is a named function, so discovery is scoped to just that area. No full assessment, no work-item menu. The client signs off on the approach before anything is built.

ShipsUse Case up front, then the FDD & TDD handover

Commercial framing is a separate question

Whether a deliverable carries LOE, hours and billing terms depends on commercial posture, not on the type. Pre-agreement work gets the full commercial treatment, because its job is to help the client decide what to fund. Work already under agreement gets none of it: effort still tracks internally, it just never becomes a client-facing number on something that is not being sold. Any of the three types can be either, so both fields get read before a document is framed.

What we own, and what we rent

The system has two layers, and they are worth keeping separate in your head, because only one of them is ours.

Layer one

The methodology

The folder structure, the skills, the reference files, the checkpoints, the evidence tiers. Written down, versioned, and improved after every engagement. It is the reason the output comes up the same way regardless of who runs it. This layer is the asset.

Layer two

The engine

Claude Code plus the MCP connections into NetSuite, Celigo, Asana and Google. Rented, swappable, and model-portable on purpose. If a better engine appears, the methodology moves onto it without being rewritten.

Why the split matters

The competitive position is not "we use AI." Anyone can rent the engine. The position is that our discovery process is written down in a form a machine executes the same way every time, with evidence discipline most firms do not apply even manually.

How instruction loads

One way to build a system like this is to write a single enormous instruction file and hope it all gets read. That fails, and it fails quietly. The OS instead hands over exactly what is needed at the moment it is needed, in three tiers.

TierWhat it holdsWhen it loads
Always on Root CLAUDE.md: folder layout, session start, the non-negotiable rules, brand, checkpoints, known traps. Every session
On demand Skills. The procedure for one kind of work, kept out of context until that work starts. When the task matches
One at a time Stage files inside a skill. Each is a self-contained contract: inputs, references, outputs, human check. At that stage

The assessment skill is explicit about it: read exactly one stage file at a time, and never work a stage without its file open. Attention stays on the current job instead of being spread thin across the whole process, and each stage names only the reference files it actually needs.

The client folder

Every client folder is stamped from a template, not assembled by hand, so the shape is identical everywhere. The separation between the four folders is doing real work. It keeps the client's own words untouched, keeps half-finished thinking out of the deliverables folder, and walls write-enabled build work off from read-only discovery.

{ClientName}/
├── CONTEXT.md       living fact sheet: accounts, contacts, status, decisions, open questions
├── .claude/         per-client settings, installs the render gate
├── source/          the client's material. Read-only. Never edited, only copied from.
├── working/         the audit trail: evidence, verification, candidates, drafts, LOE log
├── deliverables/    finals only. Nothing in progress.
└── execution/       build work, active from the execution phase onward

CONTEXT.md is the file that makes a folder self-explaining. It carries the NetSuite account IDs for production and sandbox, the sandbox refresh estimate, which connection was verified and when, the engagement type, what was promised to the client, key contacts, dated decisions, and open questions. A session reads it first, every time.

working/ deserves its own note. It holds the evidence log, the verification log, the candidate register, the drafts and the LOE log. It is not scratch paper. It is the record of how a conclusion was reached, and it is what makes a finding defensible months later when a client's admin questions a number.

The assessment pipeline

This is the machinery behind the two discovery-led types, Recovery and Implementation. A Custom Project runs the scoped version described above instead.

Discovery runs as six stages. Each has a single job, named inputs, named outputs, and a stated place where a human checks the work or does not. The numbering is real: the stages depend on each other in order.

01

Pre-onsite prep

A full read-only pass over the account before anyone walks in, so the question list is grounded in what the account shows rather than a generic checklist. Gaps between what was said and what is configured go to the top of the agenda.

produces working/onsite_prep.md and a one-page client agenda
Checkpoint 1
02

Evidence mining and the candidate register

Every material claim from every source, logged with its file, timestamp and speaker. Then an exhaustive sweep for candidate work items at a deliberately low threshold: every pain point, passing complaint, manual workaround, and every anomaly found in the account itself.

produces working/evidence.md and working/candidates.md
03

Verification and product fits

Read-only queries against the live account to confirm or refute each claim, with every query and result logged. Findings map to Power Cloud products where they fit, always with a native or third-party alternative named alongside.

produces working/verification.md
Checkpoint 2 · findings review

Approved findings become three markdown drafts. Nothing renders yet. The writing standards get read before a word of client-facing content is written.

The humanize pass runs first, so the human reviews finished prose rather than raw output. Then the draft review and the line-by-line LOE review. Only after both pass does anything render to branded .docx and .pptx.

What always ships

On a Recovery or an Implementation, three files, with deliberately different jobs. The split exists because a twenty-page PDF cannot be reviewed live in a meeting, and a deck cannot serve as the record of what was promised. A Custom Project ships the Use Case and the combined FDD & TDD handover instead, on the same principle that each artifact has exactly one job.

DeliverableJobShape
AssessmentThe source of truth. Findings, evidence, the complete work-item menu with effort and priorities, phasing, and the commercial framing..docx + PDF
PresentationThe meeting vehicle. Selective, leading with the two or three highest-impact issues and the dollar signal. Talking points live in speaker notes, not on the slide..pptx + PDF
Execution planThe technical artifact a future session builds from. Per task: problem, affected objects, build classification, steps, acceptance criteria, sandbox test plan, rollback..md, internal

Customization documents itself, in every type

Separately from all of the above, any net-new custom development carries two documents, whichever engagement it happens inside. A Use Case the client signs before build, which doubles as the SOW and states the problem, the approach, the objects involved, the assumptions and the effort. Then an FDD & TDD handover when it ships: one document whose functional half explains what the solution does and deliberately does not do, and whose technical half carries the IDs, mappings and design decisions for whoever maintains it later.

Scripts, custom applications and new integrations trigger the pair. A custom field inside a larger configuration project does not. Inside a bigger engagement it is scoped to the work item, sitting alongside the assessment rather than replacing it. The Use Case signature comes before build approval and the handover is a condition of closing the task, so a customization cannot quietly ship undocumented.

The assessment document and the implementation roadmap are largely the same document wearing different framing. Identical evidence work, identical task tables per process area. The roadmap reframes phasing as a project plan of milestones, sequencing and dependencies pointed at a target state, rather than a menu of remediation priced for a funding decision.

The methods

This is the part that separates a consultant's document from a transcription. Five habits carry most of the weight.

1. Every claim is tiered

Nothing reaches a client without a stated basis. The tiers are internal furniture and do not clutter the client's document, but they govern what may be asserted.

Verified

Confirmed by a read-only query against the account. The query and its result are logged.

Reported

Stated on a call or in a client document. Not confirmed. Never presented as fact.

Inferred

Our analysis, or an industry pattern applied. Reasoning, not evidence.

The disagreement rule

Where a call claim and the account disagree, that gap is itself a finding and gets called out rather than quietly reconciled. People misremember their own configurations. Finding the gap is often the most valuable thing discovery produces.

2. We query the account rather than take the call at face value

Access runs through NetSuite's MCP connector on a standardized read-only role, plus a small Power Cloud toolset that lets a session read the actual body of a script instead of just its name. That distinction matters more than it sounds: without it, any claim about what a script does is Reported at best, never Verified.

Any number a person repeated casually, a script count, a volume, a percentage, gets checked before it ships. The client's own admin can check ours.

The same posture extends past NetSuite to the rest of the stack, which the next section covers.

3. Nothing falls off the list silently

Surfacing every potential work item is the single highest priority of the process, and it must never depend on a consultant happening to remember something or on a transcript being complete. So candidates are captured at a low threshold from every source, and a candidate can leave the register in exactly three ways: it becomes a work item, it moves to fast-follow, or it is dropped with a written reason. It may never simply be absent.

Materiality then becomes a human decision applied to a complete list at the findings review, instead of a silent call made during extraction. On top of that sits a pattern-based backstop: a per-process-area completeness checklist that forces an explicit "not discussed" or "not applicable" for anything the sources never covered.

4. Research, do not recall

Two research obligations are mandatory rather than optional. The client's public website gets researched to build the business overview: founding, ownership, what they sell, how they operate. And any claim about what NetSuite can or cannot do natively gets checked against Oracle's documentation before it ships, with conflicts resolved in Oracle's favor. That second rule exists because a confident, wrong "NetSuite cannot do X" is the most expensive kind of error we can put in front of a client.

Client data never goes into a web query. Public identity research does.

5. Ask rather than guess

The consultant is in the loop continuously, not only at checkpoints. When the process hits a material gap, a thin inference, or a conflict between what was reported and what was verified, it stops and interviews the consultant instead of writing a plausible sentence. A speculative read is a question for a human, never an assertion in a document.

The connected stack

Verification is only ever as good as what we can actually reach. NetSuite is the one we lean on hardest, but a client's operation rarely lives in one system, and the integration layer and the systems feeding it are where a surprising share of the real problems sit.

SystemWhat we can doWhere it stands
NetSuite Full read: records, SuiteQL, saved searches, metadata, scripts and their deployments, error logs. With our own reader tooling, the actual body of a script rather than just its name. Standard on every engagement, proven repeatedly on live client accounts.
Celigo Read the integration layer directly: flows and whether they are switched on, schedules and cadence, connections, mappings, and error and job history. Used wherever a connection exists. One boundary still unconfirmed: how much of a prebuilt Integration App's settings the API actually exposes.
Shopify Read catalog, variants and options, customers and orders, and profile the whole shape of it. Proven end to end on our own development store. The route for a client's store, where their admin creates a read-only app for us, is written but has not yet been run on a live merchant.
QuickBooks Online Read and profile the entities, including chart-of-accounts structure and how completely fields are actually filled in. Proven end to end against a developer sandbox, read-only enforced at the server. The production credential for a real client is the remaining step.

Why the extraction matters

Reading a source system is not the interesting part. Profiling it is. A standard read-only pass produces entity counts, how completely fields are populated, chart-of-accounts distribution, variant and option structure, and parent-child usage, and lands as an artifact in the client's folder.

The point of that artifact is that it converts the questions nobody wants to answer in the abstract into concrete, evidenced items: how items are really identified when SKUs are sparse, whether customers have a hierarchy in practice, what the chart of accounts would need consolidating into. Those become candidate work items carrying a Verified tier, because we read the system rather than asking about it. It replaces "send us a spreadsheet and we will take a look", which is slower and produces a worse answer.

The same rules apply to all of them

  • Consent is recorded before the first query, with the date and who approved it, exactly as for NetSuite.
  • Identity check first. Confirm the connected company or store actually belongs to this client before anything else. A connector has pointed at the wrong account before.
  • Read-only during discovery, enforced where the platform allows it. The QuickBooks server is configured so write tools never load at all.
  • Credentials never touch the shared drive. They live on the connection holder's machine, one folder per client. The client's folder gets the artifacts, never the keys.
  • The credential is torn down at engagement close, and the revocation date recorded. A dormant connection into a client's systems is risk with no revenue attached to it.

Read-only is not the default, and that cost us nothing only because we checked

When the Shopify connection was first proven, an unconfigured app came back holding write access to products, orders, customers and themes, plus about ninety more permissions nobody had asked for. Nothing was written and nothing broke, but the lesson went straight into the capability register: treat any credential whose granted scopes have not been read as a write-capable key, and scope it down before it goes anywhere near a client.

And our own systems

One connection points inward rather than at a client. A scheduled job reads Power Cloud's own NetSuite every Monday for the hours logged against each customer, and drops each client's slice into their folder so the status reporting has real numbers behind it. It authenticates as an integration rather than as a person, which matters: an ordinary connection consumes a full NetSuite seat and cannot be carried by the Employee Center licences most consultants hold. Routing it through a scheduled job means nobody needs a licence upgrade to get hours in a document, and nobody handles a credential to read them.

Time entries are not reliably submitted until the Monday after the week they cover, so the hours in any summary stop at the most recent completed week while everything else runs to the minute. That is a stated window rather than missing data, and the documents say so.

Capability we borrowed rather than built

Shopify publishes its own set of skills for exactly this kind of tooling: API and schema lookup, query validation, theme templating, store management through their CLI. Seventeen of them are installed and available in every session.

We deliberately did not write a Power Cloud version. A vendor maintains their own platform's documentation better than we can, and two skills competing to answer the same question is worse than one good one. What we build is the part nobody else will: how their platform meets NetSuite in a real client's operation, and the access discipline around getting into it.

On estimates

Claude drafts LOE, a human owns it. Every line is logged with the drafted figure, the approved figure, and a reason for any change. Figures with no prior basis are flagged as such and get attention first. That log doubles as the calibration feed, which is how the baselines get more accurate over time instead of drifting.

Enforced, not trusted

Some rules are too important to leave as written instructions a session could plausibly talk itself past. Those have mechanical backstops.

MechanismWhat it does
Write guardrailIntercepts every NetSuite create, update and delete call. A sandbox connection passes through normally. A production connection forces an explicit human confirmation on every single write, even if the tool was previously allowed. A connection whose environment cannot be identified from its name also stops for confirmation. No production write can happen silently.
Render gateBlocks a deliverable from rendering while the client-facing drafts still carry mechanical copy tells. Installed per client folder. The internal execution plan is deliberately exempt. It fails open, because a broken gate must never stop a delivery.
Copy scannerA deterministic scan behind the humanize pass. Every hit is cleared or consciously waived with a reason, and a waived hit gets raised at the review.
Engagement logGenerated from what each engagement actually wrote to disk, never hand-maintained. Status reflects work done rather than a field somebody remembered to update, and it flags folders that have drifted from the standard shape.

The read-only rule during discovery is absolute and sits in the always-loaded instructions: queries, record reads and metadata only, no exceptions, even on a live production account. Writes are legitimate, but they belong to execution, which is a separately declared phase with its own guardrails, and that permission never carries back into a discovery session.

Executing the work

After sign-off the work moves into a subfolder of the same client folder, so all of the discovery history sits one level up and stays reachable. It runs write-enabled, sandbox first, always.

It has three modes, one per engagement type. A Recovery works the approved backlog, since discovery already identified every task. An Implementation derives base setup first, then runs design sessions per process area that each produce configuration tasks. A Custom Project builds one signed Use Case as one or a few tasks, with no backlog and no phasing invented around a single named deliverable.

Work starts when a person names what to work on: specific task IDs, or a phase. The tool pulls those blocks from the execution plan and works the selection rather than re-scoping the whole plan. That is deliberate, because a plan that gets silently re-opened every session is not a plan.

The step with judgment in it is planning a task, and it has three honest exits rather than one. Either enough is known and it proceeds to build, or there are open questions only the client can answer and it produces a targeted question list and pauses, or the approach itself is undecided and it builds a throwaway in the sandbox to demo before committing. Guessing a design decision is not one of the options.

Once planned, each task routes by how the change should actually be made. The preference order is deliberate: anything that can be a version-controlled, reviewable, revertible object should be one.

RouteUsed for
SDF objectScripts, workflows, custom records and fields, forms, saved searches, roles, feature enablement. The default, because it is versioned, diffable and revertible.
Config scriptAccounting and general preferences, company information, periods. Not deployable as objects, but settable programmatically and therefore auditable and repeatable from sandbox to production.
Integration changeCeligo flow configuration, mappings, schedules. A change to a live production flow counts as a production deploy and gets its own gate.
Data fixQuery plus import, or a scripted job. Sandbox first, without exception.
ManualThe genuine residue, things no programmatic path reaches. Produces a click-by-click checklist. This bucket is meant to stay small, and anything landing here has to be confirmed unreachable by the routes above.

Two ways a task gets worked

Anything carrying design judgment or production risk runs interactive, with a human at both gates. A queue of well-specified, low-risk, similar tasks (form simplifications, field adds, small validations) can instead run as a bounded autonomous batch: build, validate and sandbox-test across the set, then hand back the whole batch for review.

That autonomy stops at the sandbox. Production stays one human approval per deploy, every time, and anything the batch dropped or deferred gets logged rather than quietly skipped.

When a task closes, actual hours get recorded against it and the gap from the estimate is logged. Only delivered, human-approved work feeds the baselines.

Ongoing work

A client relationship is not only projects. Between and around them sit support tickets, dev requests, small fixes, data work, status reporting and client correspondence. All of it happens at the same bench, in the same client folder, under the same session habits and the same guardrails.

The shape holds: a folder for the piece of work, its own CONTEXT.md, the client's material in source/, the thinking in working/, and finals in deliverables/. A support engagement that starts as one call transcript and ends as a tested fix plus a customer recap has left exactly the same trail as an assessment, just shorter. Naming the Custom Project type gave a lot of this work a formal home it did not previously have.

Asana carries human-facing status while the execution plan stays the source of truth for how something is built. The two are kept in sync as tasks close. The conventions behind that (a real status on every task including "not started", an owner, hours billed to the specific task rather than a general bucket, deliverables attached to the task, next steps in the latest comment) exist because the status reporting runs on that data, and every reporting defect has traced back to input hygiene rather than to the report.

The honest part

Status reporting is now a defined skill, and the hours behind it arrive on a schedule. The rest of ongoing work is not: ticket intake, client correspondence and small fixes still run on the shared habits, the folder convention, and consultant judgment rather than a written workflow. It works, and the trail it leaves is real, but it is convention rather than machinery. Of everything described here, that remainder is the part most worth deciding whether to formalize next.

The learning loop

The system is built to improve between engagements rather than stay still, and the mechanism is deliberately slow at exactly one point.

Learnings get captured at the moment of discovery, never reconstructed from memory at the end. When a build proves an assumption about the tooling right or wrong, that goes into a dated register immediately, marked unreviewed. When a notable design or business decision gets made, it is logged as a candidate best practice.

Then, at the retro, every entry is walked with a human and gets a disposition: confirmed into the capability register, promoted into the domain playbook as practice, kept as engagement-specific, or discarded. Nothing becomes doctrine without someone saying so, and nothing disappears without a reason. That gate is why the shared library stays trustworthy as it grows.

That loop improves the domain knowledge: what we know about NetSuite, and how we work an engagement. A second, separate loop improves the OS itself. Anything about the tooling that got in your way, broke, or should exist and does not, goes into a feedback inbox: say “log this as feedback” in any session, or type /feedback. Claude drafts the entry from what just happened in the session and asks only what it cannot work out on its own, which is how much time it cost you, whether you were blocked, and whether it happens every time. Fifteen seconds, not a form. It will also offer, once, when it notices friction it caused.

Those entries are ranked by cost and frequency and worked through periodically. An item leaves the inbox as a change to the system, or as a decline with a reason written down. It never leaves silently. The one thing that kills this is politeness: an inbox with nothing in it is a finding about whether people feel able to complain, not evidence that nothing is wrong.

The same shape shows up everywhere

Capture exhaustively and cheaply, then let a human dispose of a complete list. It governs candidate work items, LOE figures, and practice learnings alike. The machine's job is to make sure nothing is missing. The human's job is to decide what matters.

What the arc is actually doing

Read it as a whole and one pattern repeats at every stage: capture exhaustively and cheaply, then put a human at the point where judgment or liability sits. The machine's job is to make sure nothing is missing. The person's job is to decide what matters, what it costs, and what goes to the client. Step 13 is what stops the whole thing being thirteen steps that produce the same quality forever.

The shared library

Cross-engagement knowledge lives in root files, and only in root files. A session working an engagement never reads another client's folder, because sibling folders are other clients' confidential material. Anything worth carrying between clients has to be generalized into the library first.

Honest limits

Worth knowing plainly, because overselling this internally would be the fastest way to lose confidence in it.

  • Access is an onboarding project, not a switch. Every engagement needs a client admin to install the connector app and stand up a dedicated role. Where that has not happened, the honest answer is that setup is the blocker, not that we proceed unverified.
  • Sandbox data lies about the present. It is frozen at its last refresh, integrations are usually disconnected, and scheduled scripts may not be deployed. Absence of activity in sandbox is not evidence of a production problem. Production is preferred for discovery precisely because the read-only rule removes the risk of using it.
  • Human review is the real bottleneck. The system produces drafts far faster than a person can vet them, and vetting is the only defense against a confident error. The checkpoints are not ceremony, they are the constraint.
  • Some things have no programmatic path. Third-party bundle installs, certain gated features, and subsidiary creation still need a person clicking. The system routes those to a checklist rather than pretending otherwise.
  • Group-call attribution is unreliable. Speaker labels on room recordings are approximate, so a name gets attached to a client-facing quote only when both the substance and the speaker are clear.
