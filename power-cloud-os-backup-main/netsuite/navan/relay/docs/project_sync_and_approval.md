# Relay T8: pending-request queue, ledger, OAuth 2.0 client, project-sync job

> Design note, draft 2026-10-09 (orchestrator, session bb920280, Mike away). Nothing here is deployed. Written against the RESTlet contract in `Power Cloud NS/CRM/docs/T3_packet.md` section 4 (script `customscript_pc_crm_api`, deployments `customdeploy_pc_crm_api_sales` and `customdeploy_pc_crm_api_travel`) and proposal `SALES_OS_PROPOSAL.md` sections 13 and 15. The relay is the existing `pc-navan-relay` (Node 22, Express, better-sqlite3, pino, systemd, Caddy; box `relay.powerclouderp.com`, see `relay/README.md` and `Navan/session.md`). This note adds four pieces to it and changes nothing in the Navan or Uber flows.

## 1. What the relay becomes

Today the relay does two jobs: fetch Navan invoice PDFs and post them to a RESTlet, and poll Uber's SFTP for trips. T8 adds:

1. **Pending-request queue**: every NetSuite mutation a session or Paco wants goes in as a pending request, is shown to a human with the resolved records and the before-and-after values, and is executed only after an authenticated approval. The relay is the gate; the model never holds credentials that reach the RESTlet (proposal section 15).
2. **Relay ledger**: one row per request id, mirroring and extending the NetSuite ledger (`customrecord_pc_op_ledger`): who asked, who approved, the canonical payload, the RESTlet answer, timings.
3. **OAuth 2.0 client**: machine-to-machine client credentials against NetSuite with two certificates, one per role mapping (sales write, travel read), token caching, rotation.
4. **project-sync job**: daily, runs `listTravelProjects` under the travel role, writes Uber's `to_uber/expense_codes` and Navan's Bill To Client feed, with the replace-list guard, last-good snapshot, heartbeat and email.

The TBA client in `src/netsuite.js` (invoice attach, Uber attach) stays as it is; it is on the grandfathered-integration migration list (TBA new-integration cutoff 2027.1).

## 2. RESTlet contract the relay codes against

`POST {restletUrl}?script=customscript_pc_crm_api&deploy=customdeploy_pc_crm_api_sales` (or `_travel`), body `{action, requestId, payload}`, answer `{ok, action, requestId, replayed, result, error: {code, message, details}}`.

| Action | Deployment | Ledgered in NetSuite | Relay treatment |
|---|---|---|---|
| resolveClient | sales | no | read, no approval |
| createEndClient | sales | yes | approval required |
| createOpportunity | sales | yes | approval required |
| updateOpportunity | sales | yes | approval required |
| logTouch | sales | yes | approval required (one-tap; see 4.3) |
| closeOpportunity | sales | yes | approval required |
| createProject | sales | yes (the builder's row) | approval required |
| listTravelProjects | travel | no | job only, never from a session |

Error codes the relay maps: `PC_API_BAD_REQUEST` (the request is wrong; shown to the requester, never retried), `PC_API_REFUSED` and `PC_API_DISABLED` (configuration; alert ops), `PC_API_REPLAY_MISMATCH` (a request id reused with a different payload; a relay bug, alert), `PC_API_IN_PROGRESS` (wait and poll the same request id), `PC_API_REFUSED_STATUS`, `PC_API_NOT_READY`, `PC_API_NOT_FOUND` (business answers; shown to the requester with the details), `PC_API_FAILED` (retry with the same request id after backoff; the RESTlet resumes from its recorded step).

Idempotency rules the relay must honor: the request id is generated by the relay once per approved request and persisted before the first call; every retry reuses it; the payload sent on a retry is byte-for-byte the canonical payload stored at approval (the RESTlet hashes it; a different payload is refused); numbers stay numbers and strings stay strings between attempts (the hash covers the raw JSON).

## 3. Pending-request queue

### 3.1 Tables (SQLite, same database as `runs`)

```sql
CREATE TABLE IF NOT EXISTS crm_requests (
    request_id      TEXT PRIMARY KEY,          -- UUID v4, generated at approval, sent to the RESTlet
    pending_id      TEXT NOT NULL UNIQUE,      -- short id shown to humans (base32, 8 chars), generated at submission
    action          TEXT NOT NULL,
    deployment      TEXT NOT NULL,             -- sales | travel
    canonical_payload TEXT NOT NULL,           -- the exact JSON string that will be sent, keys sorted
    payload_hash    TEXT NOT NULL,             -- sha256 of action + ':' + canonical_payload, same recipe as the RESTlet
    preview         TEXT NOT NULL,             -- human text: resolved records, before and after values
    requester       TEXT NOT NULL,             -- verified identity of the submitter (session user or Chat sender)
    requester_via   TEXT NOT NULL,             -- session | chat
    deal_uuid       TEXT,                      -- when the request belongs to a deal
    status          TEXT NOT NULL,             -- pending | approved | executing | done | failed | refused | rejected | expired
    approver        TEXT,                      -- verified identity of the approver
    submitted_at    TEXT NOT NULL,
    decided_at      TEXT,
    executed_at     TEXT,
    attempts        INTEGER NOT NULL DEFAULT 0,
    last_error      TEXT,
    ns_response     TEXT,                      -- the full RESTlet answer, JSON
    expires_at      TEXT NOT NULL              -- pending requests expire (default 72 hours)
);
CREATE INDEX IF NOT EXISTS crm_requests_status ON crm_requests (status, submitted_at);
```

`request_id` is generated at submission and is the primary key from the start; humans see `pending_id`, and the RESTlet sees `request_id` only once the row is approved and executed. The relay never reuses a request id across two approvals, and an expired or rejected row keeps its id so it can never be replayed by accident.

### 3.2 Endpoints (Express, under `/crm`)

All endpoints require the relay's bearer secret (`X-PC-Secret`, constant-time compare, as `/navan/invoices` does) **and** a verified identity (section 3.4). Bodies are JSON, limit 256 KB.

| Method and path | Who calls | Does |
|---|---|---|
| `POST /crm/requests` | session (Claude Code skill), Paco | Submits `{action, payload, requester, via, dealUUID?}`. The relay validates the shape locally (same rules as the RESTlet's shape part, so a bad request never waits for a human), builds the preview (3.3), stores the row as `pending`, returns `{pendingId, preview, expiresAt}`. For `resolveClient` it calls the RESTlet immediately and returns the candidates; nothing is queued. |
| `GET /crm/requests/:pendingId` | session, Paco, dashboard | Status, preview, the RESTlet answer when done. |
| `POST /crm/requests/:pendingId/approve` | the approver, through a session or Chat | Body `{approver}` taken from the verified identity, never from the client. Moves `pending` to `approved`, then executes (3.5). Returns the RESTlet answer. |
| `POST /crm/requests/:pendingId/reject` | the approver | Body `{reason}`. Moves to `rejected`. |
| `GET /crm/requests?status=pending` | dashboard, Paco's morning list | Open requests, oldest first. |
| `POST /refresh-projects` | NetSuite builder (already called by `pc_crm_project_builder_lib.js` after a project is built; secret `custsecret_pc_relay`) | Runs the project-sync job out of schedule (section 6), debounced to once per five minutes. |

### 3.3 Preview

The approval shows exactly what will change, resolved to names, so the human approves an operation and not a payload. Built at submission from read-only calls:

- `createEndClient`: company name, website, contacts to create; the `resolveClient` candidates for the same name and domain, so a duplicate is visible before approval.
- `createOpportunity`: title, customer name (SuiteQL `customer` by id), end client name, class name, partner and referral contact names, engagement type and commercial model labels, status label, staffing names, rate, deal UUID.
- `updateOpportunity`: per field, current value and new value (SuiteQL on the opportunity), and the status transition when one is in the call.
- `logTouch`: opportunity title, the note, the next contact date.
- `closeOpportunity`: title, current status, outcome, signed date or loss reason, and whether a project will follow (engagement type).
- `createProject`: title, the readiness state as the opportunity user event would show it (the relay cannot call the readiness library; it reads the same fields by SuiteQL and lists what is missing), parent that will be used, tasks that will be created.

Reads use the relay's SuiteQL access (REST query endpoint under the sales role, one request at a time, bounded) or the MCP connector's role; the design does not depend on which, only that previews are read-only.

### 3.4 Identity and approval

The gate is only a gate if the approver is who the relay says. Two channels:

- **Session (Claude Code)**: the skill calls the relay with a per-person token issued by Mike and stored in the person's machine environment (`PC_RELAY_USER_TOKEN`), never in the shared Drive. The relay maps the token to a person; `requester` and `approver` are that person. A request submitted by a person may be approved by the same person (the point is a human saw the preview, not separation of duties), except `createProject` and `closeOpportunity` on non-test deals, which a second person approves when `PC_RELAY_TWO_PERSON` is on (off in phase 1).
- **Google Chat (Paco)**: Paco posts the preview into the deal's thread with Approve and Reject buttons (Chat card actions). The approval arrives at Paco as a Chat event whose sender Google has authenticated; Paco forwards `{pendingId, approver: <sender email>}` to the relay with Paco's own service token. The relay trusts the sender only because the call came over Paco's token; a session token cannot approve on behalf of a Chat user and the reverse.

Allowed approvers are a list in the relay config (`PC_RELAY_APPROVERS`, email addresses); everyone else gets a 403 and the attempt is logged.

### 3.5 Execution

On approval the relay: marks the row `executing`; builds the RESTlet body `{action, requestId, payload: JSON.parse(canonical_payload)}`; calls the sales deployment with a fresh OAuth 2.0 token (section 5); stores the answer; sets `done` on `ok: true`, `refused` on a business code, `failed` on `PC_API_FAILED` or a transport error. Retries: `PC_API_FAILED` and transport errors retry up to 6 times with the backoff already used in `netsuite.js` (2, 4, 8, 16, 32 s), always the same request id and payload; `SSS_REQUEST_LIMIT_EXCEEDED` the same; `PC_API_IN_PROGRESS` waits 10 s and polls by re-sending (the RESTlet answers the stored result once done). After the attempts are spent the row stays `failed` with `last_error`, and the morning roll-up names it; a human either retries from the dashboard (same request id) or marks it abandoned.

Writes are serialized: one worker, one request at a time, across both deployments (a mutex in the process; the relay is one process). Reads for previews are bounded to two in flight.

### 3.6 Kill switch and rollout

Two switches, both honored before any call: the RESTlet's own `custscript_pc_api_disabled_actions` (NetSuite side) and `PC_RELAY_DISABLED_ACTIONS` (relay side, same comma-separated names). Rollout order from section 15: `logTouch` for one seller on allowlisted opportunities (`PC_RELAY_ALLOWED_OPPS`, a list of internal ids; empty means all), then intake (`createEndClient`, `createOpportunity`, `updateOpportunity`), then `closeOpportunity` and `createProject`. Test records: any title or company name starting with `ZZ TEST` bypasses the allowlist and never reaches a travel list (the builder sets the exclusion flag).

## 4. Relay ledger and reconciliation

The relay ledger is `crm_requests` plus an append-only `crm_events` table (`request_id, at, event, detail`) for submitted, previewed, approved, rejected, sent, answered, retried, expired. Daily at 06:00 PT a reconciliation reads the NetSuite ledger by SuiteQL (`customrecord_pc_op_ledger`, rows of the last 7 days) and compares: every relay `done` has a NetSuite `done` row with the same request id; every NetSuite `pending` or `failed` row older than one hour is listed; any NetSuite row the relay never sent (a request id not in `crm_requests`) is listed as foreign. Differences go into the morning email with the existing Navan summary. The saved search `customsearch_pc_recon_ledger` (T5) shows the same from inside NetSuite.

Retention: `crm_requests` rows are kept for 13 months (the previews hold customer names); `crm_events` the same. Nothing in either table holds a credential.

## 5. OAuth 2.0 client credentials with two certificates

NetSuite's machine-to-machine flow (Oracle, "OAuth 2.0 Client Credentials (Machine to Machine) Flow"): an integration record with the client credentials grant enabled; a certificate mapped at Setup > Integration > OAuth 2.0 Client Credentials (M2M) Setup to the integration, the entity (Mike's own employee record, decided 2026-10-09; no dedicated integration user) and a role; the client signs a JWT assertion with the private key and exchanges it at the token endpoint for a 60-minute access token.

Oracle requires one certificate per integration, entity and role mapping, so two mappings and two certificates:

| Mapping | Role | Deployment it may call | Certificate |
|---|---|---|---|
| sales | `customrole_pc_crm_sales_write` | `customdeploy_pc_crm_api_sales` | `pc_crm_sales.pem` |
| travel | `customrole_pc_crm_travel_read` | `customdeploy_pc_crm_api_travel` | `pc_crm_travel.pem` |

Client (`src/ns_oauth.js`, new):

```
getToken(mapping)            -> cached token for 'sales' or 'travel', refreshed when under 5 minutes of life remain
  assertion = JWT { iss: clientId, scope: 'restlets', aud: tokenUrl, iat, exp: iat + 300, jti }  signed PS256 (or RS256) with the mapping's private key, kid = certificate id
  POST tokenUrl  grant_type=client_credentials  client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer  client_assertion=<jwt>
callRestlet(mapping, deployment, body)  -> fetch with Authorization: Bearer <token>, Content-Type application/json; one retry on 401 after a forced token refresh
```

Where things live: certificate ids, the client id and the token URL in `relay.env`; the two private keys as files under `/etc/pc-navan-relay/` readable by `pcrelay` only (same as the Uber SFTP key), never in the repository, never on the Drive. Rotation: keys are generated with a one-year life; a `rotate-cert.mjs` script generates the new pair, prints the public certificate for Mike to upload as a new mapping, and the relay switches `kid` on the next run; the old mapping is deleted a week later. The token endpoint and the scope value are confirmed against Oracle's page at build time, not from this note.

The sales mapping's user is the integration entity Mike creates for "Power Cloud CRM API"; the RESTlet's allowlist checks the role script id and the deployment id, so a token minted for the travel mapping cannot run a sales action even if pointed at the sales deployment (the role would not match), and the reverse.

## 6. project-sync job

Runs daily on the box (systemd timer, 05:30 PT, after the Navan expense processor and before the Uber poll) and on `POST /refresh-projects` from the builder, debounced.

1. `listTravelProjects` under the travel mapping. Result `{searchId, projects: [{projectId, name, approverEmail}], count, excluded}`.
2. Guard (proposal section 13, replace-list safety): refuse to write when `count` is 0, when the RESTlet answered anything but `ok`, or when `count` is below `floor(lastGood * 0.8)`; alert instead. The last-good snapshot is `project_sync_snapshots` (SQLite: `at, count, body`), one row per successful run, 30 kept.
3. Uber: headerless CSV `Expense Code, Description, Employee Emails` with code `{projectId}-{slug(name)}` and the description the project name, uploaded to `to_uber/expense_codes/expense_codes_{yyyyMMdd}.csv` over the existing SFTP client. Full-list replace semantics; the guard above protects it.
4. Navan: `powercloud_customfield_{yyyyMMdd}.csv` with `Custom Field Name, Name, ID, Default, Approver` rows (`Bill To Client, {name}, {projectId}, FALSE, {approverEmail}`), uploaded to the SFTP feed Navan's account manager enables against the relay's public key. Rows with `approverEmail: null` are written with an empty approver and listed in the summary (a project with no principal). Until Navan confirms replace versus upsert, the same guard applies.
5. Summary email to the config record's Alert Email: counts, added and removed projects since the last snapshot, guard decisions, null approvers. Weekly on Monday: the MISSING_PROJECT bookings and rejected Uber codes from the integration log, with an owner line.
6. Heartbeat: the job touches `/var/lib/pc-navan-relay/project_sync.ok`; the existing watchdog alerts when it is older than 36 hours.

Free text on Navan's Bill To Client is switched off only after both feeds have run clean for two weeks (section 13).
