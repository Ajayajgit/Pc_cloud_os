# Stage 04 — Draft the three deliverables

One job: turn the approved findings into markdown drafts of the assessment document, the presentation deck, and the execution plan. Draft as markdown in `working/` first.

- Working inputs: `working/candidates.md`, `working/evidence.md`, `working/verification.md`, all reviewed at the stage-03 checkpoint
- Reference: **read `../WRITING_STANDARDS.md` before writing a word of client-facing content**; `../LOE_BASELINES.md` (hours anchors); `../PRODUCTS.md`
- Outputs: `working/draft_assessment.md`, `working/draft_proposal_deck.md`, `working/draft_execution_plan.md`
- Human check: none inside this stage; the draft review + LOE checkpoint sits in stage 05, after the humanize pass.

Engagement type (from CONTEXT.md, settled at Route first) determines the framing: everything below that mentions LOE columns, the hours roll-up, the single decision, or billing applies to the commercial assessment; omit those for the implementation roadmap and reframe phasing as a project plan.

All three deliverables always ship; they have distinct jobs.

## 1. Assessment document (.docx) — the source of truth

Order: Customer Summary, then NetSuite environment/tech stack, then straight into the tasks. No narrative executive summary; the commercial roll-up comes after the tasks. Full layout and no-judgment rules: WRITING_STANDARDS. (This structure is the commercial assessment. For an implementation roadmap, keep sections 0-3 and the appendix as-is but drop the LOE column from the task tables, drop the billing section, and reframe section 4 as a project plan, milestones/sequencing/dependencies/target-state, with no hours roll-up or funding decision.)

0. Cover: client name + logo, engagement type/dates, Power Cloud team, date, Confidential.
0a. **Table of contents** (right after the cover): a clickable TOC linking to every top-level section and to each per-area task table. The document is built to be navigated, not read cover to cover: some readers go straight to the tasks, some to the phasing, some read all of it. Every section must be reachable in one click.
1. **Customer summary** (leads the document). Research the client's public website first (required). A short, factual "Who {Client} is" paragraph (founding, founders/ownership, what they sell, stated values, from their own site), then "How they operate today" as tagged bullets (channels, fulfillment, accounting), then a short "verified scale" block (order/customer/item counts, orders per day). Describe the company; no opinion of their system, no judgment.
2. **NetSuite environment and tech stack** (high-level). A brief overview of what is verified in the account and the stack at a glance: ERP posture (single-company/OneWorld, subsidiaries), e-commerce/cart, EDI, WMS/fulfillment, payments and banking, the integration layer (iPaaS), and the scale of the custom-script estate. High-level only, not an exhaustive inventory. No "what we could not verify and why" section (verification stays internal; real gaps become open questions/next-steps).
3. **Tasks and issues** (the body, a table per process area). One table for each of Order to Cash, Procure to Pay, WMS, Record to Report, e-commerce, and platform/cross-cutting. Each row is one task, short fields only: **ID, Issue (one line), Recommendation (one line), Priority (Immediate/Near-term/Planned), LOE**, plus **Requested/Identified** and **Aligned on-site / In motion** tags where they apply. Each row's **ID links to its detailed entry in Appendix A**. Every task must trace to a candidate in `working/candidates.md`; the table is the promoted subset, the fast-follow list (below) holds the rest.
4. **Phasing and recommended start** (the document's strategic focus, placed after the task tables). This is where the document earns its keep: a clear plan of attack, developed properly, not a terse roll-up. Present it as a **phasing table** modeled on the Teppermans example: **Phase | Scope | Work Items | Business Outcome | Est. Hrs**, one row per phase, sequencing respecting dependencies (foundation/script work gates the rest). Name the recommended first phase explicitly with its hours range and the single decision needed to start. The per-phase Est. Hrs column is the effort roll-up (add a total, and state the standard exclusions beneath it: TBD/route-dependent items, per-unit work, PM/UAT ~15-20%). Do NOT add a separate consolidated per-item hours table; per-item LOE already lives in the section tables, and the phase totals recompute from those. Keep it factual; estimates are ranges, several items are discovery-led. The deck highlights this strategy selectively; here it is the complete plan.
5. **Risks, assumptions, and open items.** Risks and assumptions; areas needing deeper discovery (honest unknowns beat guesses); open questions and next steps as an action table with owner and due date/trigger.
6. **Fast-follow / supplemental items** (WRITING_STANDARDS): low-priority items noted but not urgent, a sentence each, often no LOE. Preserves future work without bloating the tables.
7. **Billing and rates:** standard terms (tasks individual, T&M at agreed rate, estimates are ranges, requirement changes need prior written approval). Match the standard language.
8. **Appendix A: task detail.** One anchored entry per task ID, linked from the §3 tables. Each entry carries the two-to-three-sentence pain with evidence, the proposed solution (product fits per stage 03), and the bolded **LOE: X hours** (anchored to `LOE_BASELINES.md` with the baseline cited, or `[no prior basis]`, or a scoped discovery number with build TBD; never invent a number to avoid a TBD). This is the only place verbose per-task prose lives.
9. **Appendix B: reference (internal).** Source inventory, account details, evidence-tier definitions.

Quote handling and the no-overreach/source-attribution guardrail: WRITING_STANDARDS. LOE/commercial sections carry no tiers, but an hours estimate built on a [Reported] claim says so.

## 2. Presentation deck (.pptx) — the meeting vehicle, not the document in slides

Unlike the document, the deck is **selective and leads with the most critical points**: the two or three highest-impact issues, the priorities, and the dollar signal. Completeness is the document's job, not the deck's. python-pptx, branded. 10-15 slides: who they are, what we heard, what we verified, what the status quo costs them, what we propose, how the engagement works, next steps.

One idea per slide. Real talking points go in **speaker notes**, not on the slide (WRITING_STANDARDS). The cross-cutting rules apply to the deck too: no overreach (the leaving-NetSuite error was a slide), verification internal (slides essentially tag-free), quote cap (two or three strongest quotes total, not a page of them), no banned filler, no em-dashes. The one deck liberty: speaker notes may be narrative and conversational (a spoken script the presenter says in their own words), which the summit praised; slide text stays concise. Priorities and phasing at a glance; headline hours; per-item detail stays in the document; discovery items high-level. The "status quo costs" beat is a stack of the client's own reported incidents with real dollar figures; never invent an annualized number. Final slide makes exactly one ask.

**Flag the custom development items.** Any task that is net-new custom development (a new SuiteScript of any type, a new custom application, a new integration or integration flow) will carry its own **Use Case before build and a combined FDD & TDD handover at ship**, per CLAUDE.md and the execution skill. Mark those tasks in the execution plan so the obligation is visible at build time rather than remembered. Do not write the Use Case now: it belongs to execution, scoped to the work item, and its LOE is the task's approved figure. What the assessment owes is the flag and an LOE that accounts for the documentation.

## 3. Execution plan (.md) — so a future Claude Code session executes with SuiteCloud SDF

Header: prod/sandbox account IDs, environment assumptions, task sequencing/dependencies. Each task is self-contained: ID + title cross-referenced to its work item; problem statement with evidence refs; affected objects; classification honestly assessed (SDF-deployable, which includes feature enablement via `features.xml` / script-automated config via an SDF-deployed `N/config` setup script, covering accounting and general preferences and company information / scripted data fix / manual config, only for ToS-gated or SDF-excluded features, subsidiaries, and what `N/config` does not expose; the execution skill carries the full routing); implementation steps; testable acceptance criteria; sandbox test plan + rollback; size S/M/L; **`Custom development: yes/no`** (yes means the task owes a Use Case before build and an FDD & TDD handover at ship); actual hours filled at completion. If a task cannot be classified without more info, say so rather than defaulting to SDF.
