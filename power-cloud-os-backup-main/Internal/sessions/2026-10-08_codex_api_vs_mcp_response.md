You are giving a read-only second opinion on an architecture choice for a small NetSuite consultancy's internal sales tooling. Reply with numbered points, each one a concrete risk, disagreement, or improvement, with the reason. Do not restate the plan. Be direct; if the recommendation is wrong, say so.

CONTEXT
- The firm (a NetSuite partner, about 10 people) is building an AI-assisted sales process in its own NetSuite production account (no sandbox exists). Claude Code sessions in deal folders do intake, proposal and close; a Google Chat bot does daily touches ("log on Acme: demo Tuesday"). Decided already: CRM stays in NetSuite; deterministic work is a script, the agent sits on top; the Create Project button (a suitelet) is being rewritten with a server-side idempotent readiness gate and a RESTlet wrapper so the close skill can call it; a daily relay job will push the active project list to Uber and Navan over SFTP via a saved-search RESTlet.
- Until now the design had the agent write NetSuite records (end-client customer, contacts, opportunity, status and next-contact updates) through the NetSuite MCP connector (the AI Connector Service), one connection per seller (three sellers plus the owner), each consuming a full user license, with a Claude Code hook that prompts a human once per session before production writes.
- Verified today against the live account: the MCP connector runs on an ad-hoc role (company info and the customfield table blocked), and the connector's server rate-limited roughly half of all parallel read calls (HTTP 429 style "rate-limiting requests"). SuiteQL GROUP BY on several columns is refused under that role.
- The entity on subcontracted deals is the end client in practice, with a class value marking the channel; the suitelet derives the billing-party parent from the class. Opportunity-to-project is the only write path that exists as code today.

THE QUESTION (from the owner): can we use an API instead of MCP to create and update leads, opportunities and projects?

MY RECOMMENDATION
1. Yes. Build one RESTlet in the account (SuiteScript 2.1, token-based auth) exposing actions: createEndClient (customer + contacts, dedupe by name/domain), createOpportunity, updateOpportunity (status, next contact, expected close, projected total, Task 1/2/3 economics), closeOpportunity (won/lost with reason), createProject (the rewritten suitelet logic, idempotent), listTravelProjects (runs the saved search). Validation and field mapping live server-side in that one place.
2. A small Python client (OAuth 1.0a TBA signing, credentials in per-machine environment variables, never on the shared drive) called by the Claude Code skills; the Chat bot and the relay call the same RESTlet from the relay box with its own token.
3. The MCP connector stays for ad-hoc reads and exploration inside a session; it is not used for writes.
4. Attribution: writes show the integration user, so each action takes a loggedBy parameter stamped onto a custom field and the memo; alternatively per-seller tokens if sellers hold licensed seats.
5. Human confirmation moves from the hook to the skill: the agent shows the exact payload and writes only on an explicit yes; the RESTlet refuses incomplete or duplicate payloads regardless of caller.
6. One integration user with a dedicated role (least privilege: customer, contact, opportunity, project, project task, saved search run) replaces three of four MCP seats.

WHAT I WANT CHALLENGED
- RESTlet with actions versus the plain SuiteTalk REST record API (no code in NetSuite): is the RESTlet worth the maintenance, or should simple field updates go through the record API and only the opinionated operations (intake, close, project) through the RESTlet?
- TBA (OAuth 1.0a) versus OAuth 2.0 client credentials (machine-to-machine) for a 2026.2 account: which should a new build pick, and does either change the license picture?
- Does a RESTlet running under an integration role bypass or weaken anything the MCP path gave (audit trail, role-based field security, the human gate), and what is the cheapest mitigation?
- Idempotency keys for createEndClient and createOpportunity: what should the natural key be so a retried call from an agent or the Chat bot never duplicates a customer or opportunity?
- Anything about running this against production with no sandbox that should change the rollout order.
- Any reason to keep MCP for writes that I am missing.

1. **TBA is the wrong choice for a new 2026.2 build.** Use OAuth 2.0 client credentials for the unattended service. Oracle says new TBA integrations will be disallowed in 2027.1, with final TBA retirement tentatively planned for 2028.1. NetSuite’s M2M flow uses a certificate-backed mapping to an entity, role, and application; plan certificate rotation from the start. Neither authentication protocol establishes a different licensing entitlement. [Authentication roadmap](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_158921905537.html), [M2M setup](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_162686838198.html).

2. **“Replaces three of four MCP seats” is not established—and conflicts with retaining MCP reads for those sellers.** MCP itself is free; user licensing is separate. Existing licensed sellers do not consume an additional user license merely by making an MCP connection. If those seats were added solely for this tooling, confirm your contractual right to provide seller access through a shared integration identity before counting savings. Sellers retaining their own MCP read connections still need their eligible identities. [Connector FAQ](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/article_4160616848.html), [License counting](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/article_0304103142.html).

3. **The RESTlet is justified here; a second generic write path probably is not.** Status, economics, class, and close dates affect your business rules, so these are not merely harmless field assignments. I would keep this small agent-facing write surface behind domain actions. Direct REST record updates become attractive when equivalent validation already runs server-side for *every* write channel. Otherwise, the hybrid creates a bypass and duplicates policy. Extract shared SuiteScript modules used by both the suitelet and RESTlet; do not copy the project logic or call the UI suitelet over HTTP. Oracle supports both approaches; this preference follows from your existing custom rules. [API comparison](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_1544786256.html).

4. **One codebase is reasonable; one authorization surface for everything is not.** Give the travel exporter a separate read-only role and deployment exposing only the fixed project search. An “own token” under the same sales-write role does not constrain it. Likewise, a bot that logs touches should not automatically acquire project creation or economics-editing authority. Share modules while separating deployment audiences and authenticated role permissions.

5. **Moving confirmation entirely into the skill weakens the human gate.** Instructions to show a payload and wait for “yes” are model behavior, not enforcement. Keep the enforced gate and bind approval to the specific operation, resolved records, before/after values, and payload hash. The cheapest robust central implementation is a pending request on the existing relay with authenticated human approval before execution. If the agent can read production credentials from its environment, it can bypass a Python confirmation wrapper. Validation prevents invalid changes; it cannot establish human authorization.

6. **`loggedBy` supplied by the agent is a claim, not reliable attribution.** Derive the requester from the authenticated relay session or verified Chat sender, and record requester, approver, integration identity, request ID, payload hash, result IDs, and outcome in an operation ledger. A mutable memo or “last logged by” field cannot represent the history. NetSuite System Notes remain available for supported changes, but the shared integration identity loses native seller-level attribution. Per-seller authentication can preserve that without requiring MCP. [System Notes](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4347506380.html).

7. **Changing to a RESTlet does not inherently bypass NetSuite security, but changing identities changes whose restrictions apply.** The integration role’s permissions replace each seller’s effective restrictions. Test record access, custom-field access, subsidiary restrictions, and seller ownership explicitly. UI-only validation and client scripts are not API safeguards; inspect workflow and user-event execution contexts too. Use explicit action and field allowlists, and never expand the role to Administrator simply to cure permission failures. Custom-field access restrictions also affect scripting. [Custom-field security](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N2841053.html).

8. **There is no safe name/domain natural key for an end client, and no universal natural key for an opportunity.** Domains can cover multiple legal entities; names change; one customer can have several concurrent deals. Resolve existing customers to NetSuite IDs, and assign a durable client UUID only after identity resolution. Assign a durable deal UUID at first intake and retain it through folder renames, proposal revisions, and channel changes. Name/domain matching should suggest candidates and require resolution when ambiguous. Persist these mappings centrally so Chat and deal-folder sessions reuse them.

9. **Separate business identity from retry identity.** Each mutation needs a request ID generated and persisted by deterministic code before sending; retries reuse it. Chat event IDs can identify redeliveries, while the deal UUID identifies the opportunity across separate messages. Store request ID, canonical payload hash, state, and result IDs. Same key and payload returns the recorded result; same key with different payload fails. Claim keys atomically—“search, then create” races. REST supports external-ID upserts, but those can update existing records and do not replace an operation ledger. [REST upsert](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/article_0807093604.html).

10. **A multi-record RESTlet needs partial-failure recovery, not just duplicate rejection.** Customer creation may succeed before a contact fails; project creation may succeed before a task or opportunity link fails. Track each completed step and make individual creations recoverable by stable identity. Explicitly handle a timeout after a successful save but before the ledger is updated. Reconcile uncertain outcomes before retrying. Do not advertise “never duplicates” until concurrent requests, lost responses, and failure after each save have been exercised.

11. **Your action model has bypasses and missing semantics.** `updateOpportunity` must not allow a caller to set won/lost and evade `closeOpportunity`. Define allowed transitions, separate reopening, and reject stale updates using an expected revision or a properly serialized compare-and-save operation. Calculate or reconcile Task 1/2/3 totals server-side. Also define lead/prospect/customer lifecycle handling: intake must not accidentally classify every unqualified lead as an established customer. A daily “log on Acme” action needs an activity record, not merely overwritten status or memo fields.

12. **Class-derived billing is a material business risk, regardless of transport.** Validate the class-to-billing-party mapping server-side and show the resolved billing party in the approval. Preserve which mapping was used when creating the project. If an end client can have direct work and subcontracted work through different partners, a single customer-level class or parent cannot represent all those relationships safely. Keep the deal-specific channel and billing relationship explicit, and reject ambiguous mappings.

13. **The observed 429s do not establish that switching transport fixes capacity.** Oracle documents that MCP shares account integration concurrency and may generate protocol requests in addition to tool calls; RESTlets also consume account concurrency. Start with serialized writes, bounded read concurrency, exponential backoff with jitter, and retries tied to the same request ID. Diagnose the refused `GROUP BY` queries separately: role, query shape, and connector restrictions are distinct possibilities. [MCP concurrency](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_0827103226.html), [RESTlet governance](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4640094112.html).

14. **Production-only development should change the rollout order substantially.** First inventory triggered scripts, workflows, emails, and downstream exports; deploy read-only validation and resolved previews. Then enable one narrow touch-update action for one seller and allowlisted records, followed by intake, and finally close/project creation. Exclude test projects from travel exports. Have an action-level kill switch, reconciliation search, and recovery procedure before multi-record writes. A dry run cannot prove save-time behavior, and reverting code does not reverse records or notifications.

15. **There is a legitimate reason to retain MCP writes, but it is not a reason to retain generic agent writes.** Per-user authentication and discoverable custom tools can be useful, especially if sellers already have licenses. Oracle supports custom MCP tools, so the same deterministic domain module could later be exposed through MCP as well as REST. For your bot and relay, direct APIs remain the cleaner interface; I would not keep MCP writes solely for audit, confirmation, or assumed extra safety. [Custom-tool support](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/article_3200541651.html).
